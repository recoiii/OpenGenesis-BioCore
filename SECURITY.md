# Security Policy

OpenGenesis-BioCore is designed as a local-first application. The v0.1.0 release exposes only a
loopback HTTP/WebSocket surface on `127.0.0.1`, performs no outbound telemetry, and does not support
remote/LAN serving. Browser authentication uses a manually supplied process bootstrap bearer only for
same-origin session establishment, followed by an independent HttpOnly SameSite=Strict session cookie.

Worker processes are launched with native argument arrays through `posix_spawn` on POSIX systems
and `CreateProcessW` on Windows. OpenGenesis-BioCore does not use `std::system`, `popen`, or shell command-string
construction for worker launch. Executable and project-root paths must be existing, canonical,
non-symlink paths before launch.


Worker stdout is a bounded, strictly validated UTF-8 NDJSON protocol channel. Unknown or duplicate
JSON fields, invalid UTF-8, raw NUL bytes, invalid Unicode escapes, type-incompatible payloads, and
lines over 64 KiB are rejected. Worker stderr is kept as a separate diagnostic channel; malformed
stdout is never silently reclassified as a diagnostic. On Windows, the current source uses an
explicit `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` so only worker stdout, stderr, and controlled `NUL`
stdin handles are inherited.


Pipeline definition, execution-plan, and plugin-manifest JSON are parsed with schema-specific bounded
parsers. Unknown or duplicate fields, invalid UTF-8, raw NUL bytes, unsupported schema versions,
invalid dependency graphs, and non-finite weights are rejected. Execution-plan snapshots are
published only under the canonical project `.biocore/runtime/jobs` tree. Symlinked reserved
directories, unsafe job path components, project escapes, and attempts to overwrite an existing
immutable snapshot are rejected. The worker verifies that the snapshot job identifier and revision
match the launch arguments before executing any module.

Plugin discovery scans only configured canonical roots and immediate non-symlink child directories.
Plugin manifests and executable entrypoints must be canonical regular files beneath the plugin
directory. Duplicate plugin IDs or module IDs reject all conflicting candidates. Registry refresh is
published atomically, so a partially invalid scan does not expose a half-built registry. Execution
plans contain resolved plugin ID, version, module type, plugin root, and executable path. Immediately
before native process launch, OpenGenesis-BioCore re-reads `plugin.json` and verifies the plugin identity, API
version, module, active-platform entrypoint, and canonical executable binding again. Plugin processes
are launched without a shell. Their stdout is not allowed to enter the worker lifecycle NDJSON stream.

The autonomous runtime measures worker liveness with a Core-owned monotonic clock. Valid ready,
heartbeat, progress, and log events refresh activity. A silent worker that exceeds the configured
timeout is force-terminated (`SIGKILL` on POSIX; `TerminateProcess` in the Windows source design) and
its active Job is persisted as `interrupted`. A native process that already exited immediately before
timeout is detected without overwriting its real exit result. Terminal or timed-out processes reserve
capacity until native reap.

OpenGenesis-BioCore uses a typed parameter and file-binding contract. User values are validated before plan
publication and are serialized into a bounded immutable per-step invocation snapshot. Managed inputs
resolve to canonical project-local regular files; upstream outputs must already exist beneath the
project outputs tree; new output destinations are generated by OpenGenesis-BioCore in a flat `outputs/` namespace.
Immediately before launch the plugin runner also requires the invocation snapshot itself to be an
absolute canonical non-symlink regular file. Plugins receive the snapshot path rather than free-form
user command-line arguments.

OpenGenesis-BioCore uses generated-output registration. A plugin cannot register an arbitrary path directly.
After a successful native plugin exit, the worker first validates every declared output and emits a
bounded Worker Protocol v2 `artifact` event only after all expected files for that step pass worker-side
validation. Core then independently re-inspects each reported output as an existing canonical,
non-symlink regular file in the flat project `outputs/` namespace before writing any ManagedFile or
provenance record. Worker processes still never write the project SQLite database. The managed-file and
`generated_artifacts` provenance rows are inserted in one SQLite transaction and conflicting provenance
is rejected rather than overwritten. A plugin that exits non-zero may leave physical partial files, but
those files are not registered as generated artifacts.

OpenGenesis-BioCore batches sibling output artifacts at the Core step boundary. Artifact events are buffered
until the matching step progress event; Core then re-inspects every output and persists all sibling
ManagedFile/provenance pairs in one `BEGIN IMMEDIATE` SQLite transaction. Any sibling conflict rolls
back the complete batch, and Job progress is updated only after batch registration succeeds. Failed or
interrupted jobs invoke a best-effort partial-output cleaner. It protects all registered artifacts and
only quarantines regular, non-symlink files in the flat `outputs/` namespace whose filenames start with
the affected job ID. Eligible files are atomically renamed into project-local
`.biocore/quarantine/outputs/<job-id>/`; files belonging to other jobs, registered artifacts, symlinks,
and non-regular entries are not followed or deleted.

OpenGenesis-BioCore stores a durable recovery checkpoint on each generated-artifact provenance row. The
checkpoint is written in the same artifact batch transaction, so a Core crash after artifact commit but
before the later Job-progress update can be reconciled at the next recovery pass. DB-active Jobs whose
native session ownership is no longer trustworthy are conservatively transitioned to `interrupted`
using the maximum of persisted Job progress and the durable artifact checkpoint; they are never
automatically relaunched. Quarantine retention is restricted to old regular, non-symlink files beneath
`.biocore/quarantine/outputs/<job-id>/`; fresh files, future-dated files, symlinks, non-regular entries,
and paths outside the canonical Job quarantine directory are not purged.

OpenGenesis-BioCore stores SHA-256 integrity metadata for newly registered generated outputs. Core computes the
hash while independently inspecting the physical output and repeats path, type, size, and modification-
time checks after hashing. Application validation and project-schema-v5 SQLite triggers both require a
lowercase SHA-256 for new generated outputs. Legacy checksum-null artifacts are preserved rather than
silently assigned fabricated hashes; verified download fails closed for those rows. Before preparing a
download, Core revalidates the flat `outputs/` path, provenance binding, non-symlink regular-file status,
size, and a freshly computed SHA-256. Same-size content replacement therefore fails with a checksum
mismatch. The internal absolute content path returned to a future server adapter is not part of the
report serialization and must never be exposed to a client. Static HTML reports escape user-controlled
text fields and JSON reports escape control characters, quotes, and backslashes.

Plugins are nevertheless native trusted-local code. OpenGenesis-BioCore does not yet verify signatures or publisher
trust, sandbox plugin processes, restrict their filesystem/network access, or apply CPU/memory limits.
Installing a plugin is therefore still equivalent to installing a native executable from that publisher.

The current process and transport adapters do not yet eliminate executable/handle-replacement TOCTOU
races, create process groups/job objects, provide graceful user cancellation, or persist native
heartbeat/PID/session ownership. Native Windows runtime behavior is not yet validated. Manifest and
execution-plan publication do not yet issue explicit `fsync`/`FlushFileBuffers`, and standard-library
path checks cannot eliminate every TOCTOU race. Recovery logic restores durable database state after the
artifact-batch/Job-progress crash window, but it does not adopt or terminate a native orphan process
from a prior Core instance, automatically resume interrupted Jobs, reconstruct artifact events that
never reached the durable artifact transaction, or reconcile runtime/execution/invocation snapshots.
Quarantine retention is currently a fixed Application policy based on filesystem modification time and
has no user-facing setting. SHA-256 verification narrows content-substitution risk but does not yet use
an OS handle-based immutable serving boundary; a future HTTP adapter must avoid a long verification-to-
streaming gap or unsafe path reopening. Hashing is synchronous, and legacy generated outputs are not
automatically backfilled. These are documented pre-release boundaries rather than security guarantees.

Do not include biological data, access tokens, passwords, absolute patient file paths, or personally
identifiable information in issue reports or logs.

A formal vulnerability reporting channel will be defined before the first public release.


## Local HTTP boundary

The first web boundary is local-only. The composition root binds to `127.0.0.1`; the optional Drogon
adapter independently rejects non-loopback bind addresses. `/api/v1/health` is public, while the remaining
REST routes require a process-lifetime bearer token generated from the operating-system CSPRNG. The token
is not persisted in project SQLite or project files. URL query-token authentication is intentionally not
implemented.

HTTP requests are size-bounded, UTF-8/NUL checked, and strictly routed. The v1 route parser rejects query
strings, fragments, percent-encoded paths, and traversal atoms until explicit semantics are implemented.
Verified artifact absolute paths are carried only as internal adapter descriptors and must never be
serialized into API JSON/HTML. The optional Drogon adapter streams an already verified artifact from the
local filesystem. A verification-to-open TOCTOU window remains; native handle-based immutable serving is
not yet a security guarantee.

The validation environment does not contain Drogon, so no native Drogon compile/run or Windows/MSVC web
server validation is claimed. Builders that require Drogon should configure with
`BIOCORE_REQUIRE_DROGON=ON`, which fails closed when the dependency is absent.


## Prepared submission and runtime activation

A REST Job is not scheduler-runnable until OpenGenesis-BioCore has resolved an exact pipeline ID/version, resolved plugin modules and bindings, published an immutable execution-plan snapshot, and committed the queued Job plus `job_execution_plans` association. The scheduler refuses missing or revision-mismatched associations. Schema-v6 triggers independently validate queued status, pipeline identity, and launch revision for direct association writes.

The local server now runs a background WorkerRuntime. To prevent multi-statement transactions from interleaving on one SQLite handle, the final composition root uses separate API and runtime WAL connections; the HTTP adapter is restricted to one request worker in Core 0.1. Scaling request concurrency requires per-request database connections or a reviewed pool.

Execution-plan filesystem publication cannot be atomically committed with SQLite. A crash after publication but before DB activation may leave an orphan snapshot, but no queued prepared association exists and the scheduler cannot run it. A crash after DB activation but before HTTP 201 may leave a valid queued Job that the client did not observe; submission idempotency keys are not yet implemented.


## Browser managed-file import and release hardening

Browser file contents are transferred to localhost in sequential chunks capped at 1 MiB, with a declared
file-size cap of 8 GiB and no query-token authentication. Binary chunk bodies are the only upload bodies
that bypass ordinary UTF-8/NUL validation; route metadata remains bounded and validated. Staging is
restricted to `.biocore/runtime/browser-uploads/<upload-id>` and final publication uses a rollback-safe
rename into the normal managed-input namespace. REST managed-file DTOs do not disclose original, managed,
or project-relative filesystem paths.

Upload sessions are process-local and bounded to eight active sessions. Release hardening reclaims sessions
after 30 minutes without successful activity using the existing Application-owned monotonic-clock port;
a successful chunk refreshes activity. Reclamation discards only the exact OpenGenesis-BioCore-owned staging session.
Sessions are not resumable across process restart.

The release exposes `biocore --init-project` as a composition-root use of the existing
ProjectService/workspace/catalog boundaries. The catalog database must remain outside the project workspace;
symlinked/unexpected roots are rejected. Native Windows/MSVC execution remains a final release evidence gate
and is not inferred from Linux validation.
